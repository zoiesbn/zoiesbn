From Figma to Code and Back Again

Some decisions need a shared design file. Others become clearer when you try them in a working page. The useful part is knowing when to move between the two.

By Zoha Sobhani · August 26, 2026 · 4 min read

A layout can look finished in Figma and still need work in the browser. A longer heading changes the balance. A narrow screen exposes a spacing problem. An interaction feels slower than it did in the prototype.

Those differences give me a reason to return to the design. I can revise the layout, try it again, and see whether the change helps. The file and the working page each show things the other can't.

How much I need to settle in the file first depends on the work and the people building it. A change shared across several teams needs a different approach from an early idea that a small team wants to test.

When the team needs a shared reference

In a larger organization, the Figma file may be where product managers, engineers, researchers, and QA agree on what a feature should do. Someone who wasn't in the design discussion still needs to understand the result.

That's when I want the file to answer practical questions. What happens when the content is empty? Which component should be used? What should someone see after a failed action?

  • Show the steps in the flow, including errors and less common cases.
  • Use shared components where they fit, and explain exceptions.
  • Prototype interactions that are hard to explain with static screens.
  • Write down constraints and decisions that affect implementation.

These details give developers and QA something concrete to work from. They also make it easier to spot disagreements before several teams build different answers to the same question.

When a working prototype answers the question sooner

On a smaller team, the immediate question may be whether an idea is useful at all. Spending days documenting every state can be premature if a short test would change the direction.

I'd start with the smallest prototype that lets someone try the task. Then I'd watch where they hesitate, what they misunderstand, and whether they reach the intended result.

Figma may be enough for that test. If the question depends on real content, responsive behavior, or an interaction the prototype can't represent well, a working page may be more useful. I'd choose the tool around the question we need to answer.

Keep the developers close to that work. A quick conversation about what's feasible can save time before a design goes too far. After the test, record the decisions the team will need for the next version.

Match the detail to what could go wrong

A payment flow needs clear error handling, constraints, and agreement between the people designing and building it. An early onboarding idea may only need a prototype and a few conversations before the team decides whether to continue.

Even a small team needs careful documentation when a mistake would be costly. And a large team can test an uncertain idea before writing a full specification.

I find it more useful to ask what another person needs to make the next decision. If a note prevents a repeated question or an implementation mistake, keep it. If nobody can explain how a document will be used, reconsider the work going into it.

Bring what you learn back into Figma

A code prototype can reveal a problem that wasn't obvious in the design file. Bring that finding back to the team: show the page, explain what changed, and decide whether the shared design needs updating.

Figma describes this exchange as a design-to-code loop. In practice, I'd treat it as a reason to keep reviewing the implemented experience instead of considering the design finished at handoff.

That doesn't require every designer to write production code. It does require enough understanding to discuss layout, content, and behavior with the people who do.

Review the decisions in the product

When a feature is ready to review, walk through an actual task. Try longer content and a smaller screen. Compare the result with the decisions in the file, and talk through any differences with the developer.

If the implementation reveals a better answer, update the shared reference. If it exposes a problem, record what needs fixing and who will follow up. Those details matter more than having a file that looks finished while the product behaves differently.
